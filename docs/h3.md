# HTTP/3 (issue #20): what exists, and what QUIC still needs

**Verdict: QUIC cannot be built on the current platform. The HTTP/3 layers above it are done and tested.**

| Piece | Module | State |
| --- | --- | --- |
| Variable-length integers, HTTP/3 frames, SETTINGS, error codes (RFC 9000 section 16, RFC 9114 section 7 and 8) | `http/h3frame` | done, tested against the RFC 9000 appendix A vectors |
| QPACK (RFC 9204): static and dynamic table, encoder and decoder streams, blocked streams | `http/qpack` | done; appendix B reproduced byte for byte; checked against libnghttp3 in both directions |
| HTTP/3 connection (control stream, SETTINGS, request streams, GOAWAY, errors) | `http/h3` | done, sans-IO: runs over any set of streams, tested Eider to Eider over in-memory ones |
| QUIC transport (RFC 9000, 9001, 9002) | none | **not started: blocked on three dependencies below** |

## 1. Assessment: what QUIC needs from the platform

QUIC is a UDP protocol with its own encrypted packets, a TLS 1.3 handshake carried in its CRYPTO frames, and loss recovery
and congestion control. Checked against the toolchain used here (Eider 0.8.0, `std/net.ei`, `packages/crypto`) and the
sibling `eider-tls` 0.8.0.

### UDP sockets (`std.net`): enough for a minimal transport

`std.net` has datagram sockets: `socket(family, DATAGRAM, nonblock)`, `bind`, `send_to(s, data, to)`, `recv_from(s, max)`
(a `Datagram` with the sender), `local_addr`, and `fd.wait_ready` / `std.poll` work on them. Checked by a loopback
exchange on non-blocking sockets (`recv_from` with nothing queued is an `Err("recvfrom: Resource temporarily
unavailable")`, so "nothing yet" is a string match, not an `Option` as `try_recv` has for TCP).

What it lacks, from the most to the least important for QUIC:

- **No ancillary data at all** (`recvmsg`/`sendmsg` control messages) and `set_option` only knows the options in
  `net.REUSE_ADDR ... SEND_TIMEOUT_MS`. So: no ECN (IP_TOS / IP_RECVTOS), no packet info (IP_PKTINFO: a server bound to a
  wildcard address cannot reply from the address the client used, which RFC 9000 section 9 and multi-homed hosts need), no
  don't-fragment bit (IP_MTU_DISCOVER / IPV6_DONTFRAG: DPLPMTUD, RFC 9000 section 14, cannot be done; a transport stays at the
  1200-byte minimum datagram), no GSO / GRO / `sendmmsg` (one system call per datagram, which costs throughput, not
  correctness).
- None of these stops a working transport: ECN is optional, a server bound to one address needs no PKTINFO, 1200 bytes is
  the mandated floor. They do cap how good it can be.

### eider-tls: the blocker

QUIC (RFC 9001) uses TLS 1.3 only for the handshake and takes the secrets out of it. It needs the handshake as a
message-level API. `eider-tls` has the parts but not the API:

- `tls.handshake` has the message codecs (ClientHello, ServerHello, EncryptedExtensions, Certificate,
  CertificateVerify, Finished, KeyUpdate) and `tls.keys` the key schedule (`early_secret`, `handshake_secret`,
  `master_secret`, `derive_secret`, `expand_label`, `traffic`, `finished`), all public.
- But the handshake is driven by `client.ei` / `server.ei` over a `conn.Conn` that owns the TLS record layer: they read
  and write records on a stream, derive keys into record protectors, and give no access to the traffic secrets. There is no
  way to feed a ClientHello in as bytes and get the flight and the secrets out per encryption level
  (Initial / Handshake / 1-RTT).
- `ClientHello` and `EncryptedExtensions` have a **fixed extension set**: server_name, ALPN, supported_groups,
  signature_algorithms, supported_versions, key_share, cookie, and PSK / early_data flags. There is no
  `quic_transport_parameters` (extension 57, which RFC 9001 section 8.2 requires in both directions) and no way to add one;
  a client even refuses an EncryptedExtensions with an extension it did not ask for.
- No PSK, no session tickets, no resumption, no 0-RTT (stated in `client.ei` and `server.ei`). QUIC without them works
  (1-RTT only, no early data), so this is a later feature, not a blocker.
- Key update is not TLS's in QUIC (RFC 9001 section 6 derives the next secret with the label `quic ku`); `keys.expand_label`
  already serves for that and for the Initial secrets (`client in`, `server in`, `quic key`, `quic iv`, `quic hp`).

### eider-crypto (the toolchain's `packages/crypto`): one primitive missing

- Present: AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305 `seal`/`open` with a caller-chosen 96-bit nonce
  (`nonce_for_sequence` is the QUIC packet-number nonce), HKDF extract/expand, HMAC, SHA-256/384, X25519, P-256, Ed25519,
  random bytes. That covers packet protection, the Initial keys (HKDF with the version's salt) and the Retry integrity tag
  (AES-128-GCM with the fixed key and nonce of RFC 9001 section 5.8).
- **Missing: header protection (RFC 9001 section 5.4).** It needs a raw single-block AES encryption (AES-ECB of one block,
  with the sample as input) or the raw ChaCha20 block function (counter and nonce from the sample). `crypto` exposes only
  the AEAD constructions: the AES-GCM counter block always ends in a small counter, so a 16-byte sample cannot be turned
  into a block encryption through `seal`, and ChaCha20-Poly1305 reaches only block counter 1. This cannot be worked around
  without writing AES (or ChaCha20) in Eider outside the toolchain's audited backend, which this repository does not do.

### Verdict and the smallest asks

QUIC feasible now: **no**. The smallest set of additions, by repository:

1. **`eider-lang`, `packages/crypto`** (the toolchain): `aes_encrypt_block(key: AeadKey-or-bytes, block: List[u8]) ->
   Result[List[u8], Error]` for AES-128/256 and `chacha20_block(key, counter: u32, nonce: List[u8]) -> Result[List[u8], Error]`.
   Two functions; header protection is then five lines.
2. **`eider-tls`**: a module (say `tls.quic`) with a message-level handshake: `client(cfg, transport_params)` /
   `server(cfg, transport_params)` giving a state machine with `feed(level, bytes)`, `poll() -> List[(level, bytes)]`,
   `traffic_secrets(level)` (the read and write secret of the Handshake and 1-RTT levels, and the negotiated suite), the
   peer's `transport_params`, the negotiated ALPN, and errors as TLS alerts (QUIC maps them to CRYPTO_ERROR 0x100 + alert).
   It is a refactoring of `client.ei` / `server.ei` away from `Conn`; the handshake codecs need a generic extension list
   (to carry extension 57), an empty legacy_session_id and no change_cipher_spec compatibility records (RFC 9001 section 8.4).
3. **`eider-lang`, `std/net.ei`** (optional, for quality not function): `try_recv_from` returning an `Option`, `recvmsg`-style
   receive with the destination address and TOS, and the options `RECV_TOS` / `TOS` / `DONTFRAG` / `PKTINFO`.

With 1 and 2 the transport (packets and frames, ack and loss recovery with the RFC 9002 NewReno controller, flow control,
stream state, connection IDs and migration off) is pure logic that can be written and tested in Eider against `h3`
below, and, because libngtcp2 is commonly installed (`libngtcp2.so` was found here, with its crypto helpers), checked against
`ngtcp2` the way `http/qpack` is checked against `nghttp3`.

## 2. `http/h3frame`

`import http.h3frame`. RFC 9000 section 16 varints (`put_varint`, `get_varint`, `encode_varint`, `varint_len`,
`put_varint_n` for non-minimal forms), the frame types and error codes, an incremental `Decoder`, and the encoders
(`frame`, `data`, `data_header`, `headers`, `settings`, `goaway`, `max_push_id`, `cancel_push`, `grease_frame`, `stream_type`).

The decoder checks what RFC 9114 says before anything else sees a frame (see the module comment for the whole list): DATA is
streamed in `Chunk`s and never buffered, other frames are refused over `max_payload` (H3_EXCESSIVE_LOAD) from their
header, unknown and reserved ("grease") frames are skipped without buffering, HTTP/2 frame types, wrong-stream frames, the
SETTINGS-first and SETTINGS-once rules, size rules and the HTTP/2 settings ids are errors with the code the RFC names.
`Decoder.idle()` says whether the stream may end here.

## 3. `http/qpack`

`import http.qpack`. `decoder(max_capacity, max_blocked, max_list)` and `encoder(peer_max_capacity, peer_blocked)`.

- Decoder: `receive_encoder(bytes)` (incremental: an instruction may arrive in pieces), `decode_section(stream, bytes)`
  giving `Ready(section)` or `Blocked` (the section is kept and comes back from `receive_encoder` when its entries
  arrive), `cancel_stream`, `take_output()` (section acknowledgments, cancellations, insert count increments).
- Encoder: `set_capacity`, `encode(stream, fields)` giving the section and the encoder stream instructions, `insert_field`,
  `duplicate`, `receive_decoder(bytes)`. Never exceeds the peer's blocked-streams limit, never evicts an entry a
  section the peer has not acknowledged names, writes `authorization`, `proxy-authorization`, `cookie` and `set-cookie`
  (and `Encoder.sensitive`) as never-indexed literals. Not done: the draining index of RFC 9204 section 2.1.1.1.
- Limits: strings (`max_string`, 8 KiB), integers (2^62), decoded field section (`max_list`, the fields over it are dropped
  after the table has been kept in step), blocked streams (an error past the advertised number), table capacity, entry size.
- Huffman coding and prefix integers are `http/hpack`'s.

Validation: the static table (all 99 entries) equals what libnghttp3 decodes for each index; RFC 9204 appendix B (B.1 to
B.5) is read by the decoder and written byte for byte by the encoder; every split of an encoder stream gives the same
table; a corpus of malformed sections, encoder stream instructions and decoder stream instructions gets the right error
code; 300 field sections through a 300-byte table with late delivery agree entry for entry between both sides.
`tests/qpack_interop.sh` runs 4 table sizes x 5 seeds x 300 random sections through libnghttp3 both ways (it needs
only the shared library; `skip` without it).

## 4. `http/h3`

`import http.h3`. `h3.client(cfg)` / `h3.server(cfg)` give a `Conn`, a state machine with no I/O (module comment has the
interface). The stream interface it runs over, which a QUIC connection provides directly:

    in:  conn.recv(stream, bytes, fin)    conn.recv_reset(stream, code)    conn.recv_stop_sending(stream, code)
    out: conn.poll() -> [Write(stream, bytes, fin) | ResetStream(stream, code) | StopSending(stream, code) | CloseConn(code, why)]

and the user side: `send_request`, `send_headers` (interim and final heads, trailers), `send_data`, `finish`, `reset`,
`stop_reading`, `goaway`, `close`, `take_events()` (`PeerSettings`, `Informational`, `Headers`, `Data`, `Trailers`,
`Finished`, `StreamReset`, `StreamError`, `GoAway`, `Closed`). `h3.pump(a, b)` connects two connections in memory.

Covered by `tests/h3_test.ei`: the startup bytes, the SETTINGS exchange, GET and POST with bodies, trailers and interim
responses, delivery one byte at a time, the dynamic table shrinking requests from 52 to 11 bytes, a request that arrives
before its QPACK entries, GOAWAY (including a request rejected after it), the peer's MAX_FIELD_SECTION_SIZE, connection
errors (control stream, QPACK streams, push, frame order, ids) and malformed messages (stream errors, with the connection
surviving), the sending-side checks, reset and STOP_SENDING, 20 concurrent requests, and 600 rounds of random bytes that
reach every stream type without a trap.

Not done: server push (RFC 9114 section 4.6), extended CONNECT, WebTransport and datagrams (RFC 9297: they need QUIC's
DATAGRAM frames), 0-RTT, RFC 9218 priorities, and anything about the transport (stream flow control, connection IDs, ...).
